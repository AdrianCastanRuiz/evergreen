Evergreen — UX Design Validation Report

_bmad-output/planning-artifacts/ux-designs/ux-evergreen-2026-07-01/

DESIGN.md is strong: canonical section order intact, every color has a hex value, every {path.to.token} reference in both files resolves, and the shadcn-shaped token naming is disciplined. EXPERIENCE.md is adequate but not airtight as a downstream contract: two top-level family-facing IA surfaces (Menu, News & Documents) have no real component definition anywhere, no state is defined for permission-denied/role-gated access despite RBAC/multi-tenancy being the PRD's headline technical requirement, and three of the four Key Flows omit the explicit failure path the fourth flow and both calibration examples provide. None of this is broken — a human downstream consumer can infer sensible defaults — but an AI story-dev consumer would have to invent load-bearing behavior that should have been committed here.

Accessibility lens: the spine mostly honors its stated "basic good practices" bar in the places it explicitly designed for it, but two concrete gaps would quietly undermine that bar for the stated older/less-tech-fluent audience: muted-foreground gray fails AA contrast on exactly the meta text (dates/times) this persona relies on, and the photo gallery — the single most emotionally load-bearing feature in Flow 1 — is swipe-only with no tap fallback, contradicting the team's own stated swipe-gesture caution elsewhere.

Accessibility review

review-accessibility.md

The spine mostly honors its stated "basic good practices" bar in the places it explicitly designed for it: RSVP/upload/validation states are properly text-paired, destructive and secondary color pairs are comfortably AA-compliant, and touch targets are called out for the highest-traffic components. But two concrete gaps would quietly undermine that bar for the stated older/less-tech-fluent audience.

Critical

muted-foreground fails AA contrast on the exact meta text this persona needs

DESIGN.md Colors/Typography; EXPERIENCE.md Accessibility Floor
{colors.muted-foreground} (#7A7A7A) fails WCAG AA for normal text against both background (#FFFFFF, ≈4.29:1) and muted (#F8F8F8, ≈4.04:1) — both below the required 4.5:1. This is the exact color used for timestamps, event date/time, photo captions, inactive tab labels, at the smallest type size (13px caption). Directly contradicts EXPERIENCE.md's own Accessibility Floor claim.
Fix: darken muted-foreground to roughly #5C5C5C/#5E5E5E (≈4.6–4.7:1 on white) or increase caption size, and correct the Accessibility Floor claim to reflect the real ratio.
High

Gallery viewer is swipe-only with no tap fallback

EXPERIENCE.md Component Patterns — Gallery tile / full-screen viewer; Interaction Primitives
Elsewhere the team explicitly reasoned that swipe gestures are risky for this audience ("no swipe-to-delete... keeps the surface predictable"), but that caution wasn't applied to the gallery's primary navigation gesture — and photos are the emotional core of Flow 1 (Maria's climax moment). A user who doesn't discover the swipe gesture is stuck on the first photo.
Fix: add visible tap zones or arrow affordances alongside swipe, matching the same "predictable, non-hidden-gesture" logic already applied to list rows.
High

13px caption floor compounds the contrast failure

EXPERIENCE.md Accessibility Floor; DESIGN.md typography.caption
Event times/locations, photo dates, meal-day labels sit at the smallest text size AND a failing contrast ratio — a double penalty on meta information explicitly called out as important for an older audience.
Fix: fix the contrast first; separately consider a 14–15px caption floor as a more forgiving unscaled default.
Medium

Primary green on white / white on primary has almost no AA margin

DESIGN.md Colors [ASSUMPTION]; EXPERIENCE.md Accessibility Floor
Both pairings compute to ≈4.69:1 — technically passing but with almost no margin, and the hex is flagged [ASSUMPTION] (visual analysis, not confirmed brand guideline).
Fix: when the real brand hex is confirmed with the client, explicitly re-verify this pairing.
Medium

Calendar "has event" dot is an uncovered color-only signal

EXPERIENCE.md Component Patterns — Event calendar cell; Accessibility Floor
{colors.accent} dot contrast against cell background is ≈2.94:1, under the 3:1 UI-component guidance, with no numeric/text fallback, and not covered by the stated "no color-only signaling" rule.
Fix: extend the no-color-only rule to the calendar dot (e.g., a small count badge) and/or deepen the teal to clear 3:1.
Medium

Card/input hairline borders are nearly invisible

DESIGN.md Elevation & Depth, Colors
border (#D8D8D8 ≈1.42:1) and border-strong (#D1D1D1 ≈1.53:1) are far below the 3:1 guidance for perceivable UI boundaries, and Elevation & Depth relies on this hairline alone in default state.
Fix: darken the default border token or add subtle background-fill differentiation so boundaries are legible without focus state.
Medium

Touch-target minimum not stated for several interactive elements

EXPERIENCE.md Accessibility Floor; Component Patterns — Event calendar cell, Meal selection row
form-input, event-calendar-cell day cells, and the meal "Cancel order" text-link aren't in the explicit 44pt/48dp list. Calendar day cells are highest risk (7 columns per week vs. 44pt floor is a real design tension).
Fix: add these to the explicit touch-target list and flag the calendar-cell/7-column tension for implementation.
Medium

Resident switcher has no rule for pill-row vs. dropdown, no scroll affordance

DESIGN.md components.resident-switcher; EXPERIENCE.md Component Patterns
For a less tech-fluent user with 3+ linked residents, an undiscovered horizontal-scroll interaction risks a resident's content never being found.
Fix: pick one pattern or a clear threshold (e.g. pill row for 2–3, dropdown for 4+), and specify a visible scroll cue.
Medium

No default stated between Events list vs. calendar view

EXPERIENCE.md Information Architecture; Key Flows — Flow 1
Calendar/grid view is inherently higher cognitive load than a list for a less tech-fluent audience; Flow 1 implicitly uses the list without the spine ever formalizing that as the default.
Fix: explicitly set list as the default view for family users, with calendar as an optional secondary toggle.
Low

Web portal focus order/Esc behavior only asserted, not specified

EXPERIENCE.md Accessibility Floor
"Follows shadcn/ui defaults" isn't checkable against anything concrete — matters most for staff on a mobile-browser portal.
Fix: at minimum, state that opening/closing a modal or the mobile nav sheet traps and returns focus.
Low

Hover-only accent-blue fill is sub-AA

DESIGN.md Colors
accent-blue-hover with white text ≈4.29:1 — low real-world impact since hover doesn't apply on touch and is transient on desktop.
Fix: low priority; verify only if this fill ever renders static label text.
Low

Teal accent described as "info-toast background" but not used that way

DESIGN.md Colors vs. Components — toast-banner
Prose inconsistency risks an implementer wiring in the lower-contrast teal instead of accent-blue for the info toast.
Fix: remove "info-toast backgrounds" from the teal-accent description to match the component spec.
