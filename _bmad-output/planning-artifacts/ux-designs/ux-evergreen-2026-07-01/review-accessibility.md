# Accessibility Review — evergreen

## Overall verdict

The spine mostly honors its stated "basic good practices" bar in the places it explicitly designed for it: RSVP/upload/validation states are properly text-paired (not color-only), destructive and secondary color pairs are comfortably AA-compliant, and touch targets are called out for the highest-traffic components. But two concrete gaps would quietly undermine that bar for the stated older/less-tech-fluent audience: the `muted-foreground` gray fails AA contrast on exactly the meta text (dates/times) this persona needs, and the photo gallery — the single most emotionally load-bearing feature in Flow 1 — is swipe-only with no tap fallback, contradicting the team's own stated swipe-gesture caution elsewhere. A handful of medium-severity gaps (calendar "has event" dot as an uncovered color-only signal, near-invisible card/input borders, incomplete touch-target coverage, an underspecified resident-switcher scroll affordance) round out real, audience-relevant risk rather than WCAG purism.

## Findings

- **critical** `{colors.muted-foreground}` (`#7A7A7A`) fails WCAG AA for normal text against both `{colors.background}` (#FFFFFF, ≈4.29:1) and `{colors.muted}` (#F8F8F8, ≈4.04:1) — both below the 4.5:1 required for normal-size text. This directly contradicts EXPERIENCE.md's Accessibility Floor claim that "`{colors.muted-foreground}`... against `{colors.background}` / `{colors.muted}`" meets AA. This is the exact color used for timestamps, event date/time text on `event-list-item`, photo captions, and inactive tab-bar labels — set at the smallest type size in the system (`typography.caption`, 13px). (DESIGN.md Colors / Typography; EXPERIENCE.md Accessibility Floor). *Fix:* darken muted-foreground to roughly `#5C5C5C`/`#5E5E5E` (≈4.6–4.7:1 on white) or increase caption size, and correct the Accessibility Floor claim to reflect the real ratio.

- **high** The full-screen gallery photo viewer is navigated by swipe-left/right only, with no stated tap-based next/prev affordance ("Swipe left/right between photos... Pinch-to-zoom... Swipe down or tap close to return"). Elsewhere the team explicitly reasoned that swipe gestures are risky for this audience ("No swipe-to-delete or swipe actions on list rows in V1 — keeps the surface predictable for a less tech-fluent family audience"), but that same caution wasn't applied to the gallery viewer's *primary* navigation gesture — and photos are the emotional core of Flow 1 (Maria's climax moment). A user who doesn't discover or trust the swipe gesture is stuck on the first photo. (EXPERIENCE.md Component Patterns — Gallery tile / full-screen viewer; Interaction Primitives — Swipe). *Fix:* add visible tap zones or arrow affordances (leading/trailing edge tap, or small prev/next chevrons) alongside swipe, matching the same "predictable, non-hidden-gesture" logic already applied to list rows.

- **high** The muted-foreground contrast failure (above) compounds with the 13px caption floor on exactly the content this persona relies on most: event times/locations, photo dates, and meal-day labels. Even with system font-scaling respected (which helps users who've *already* increased their OS text size), the unscaled default pairs the smallest text in the system with a contrast ratio that already fails AA — a double penalty on meta information explicitly called out as important for an older audience. (EXPERIENCE.md Accessibility Floor; DESIGN.md typography.caption). *Fix:* raise the contrast fix above first; separately consider a 14–15px caption floor as a more forgiving unscaled default, since 13px is unusually small to serve as the whole system's floor for this persona.

- **medium** White text on `{colors.primary}` fill (button-primary, active resident-switcher pill, active tab) and `{colors.primary}` text on white (links) both compute to ≈4.69:1 — technically passing AA (4.5:1) but with almost no margin. These hex values are flagged `[ASSUMPTION]` (derived from visual site analysis, not a confirmed brand guideline); if the real brand green is even slightly lighter once confirmed, this pairing fails outright. (DESIGN.md Colors, `[ASSUMPTION]` note; EXPERIENCE.md Accessibility Floor). *Fix:* when the real brand hex is confirmed with the client, explicitly re-verify this pairing rather than assuming the placeholder value's near-miss margin carries over.

- **medium** The calendar "has event" dot (`{colors.accent}`, `#3DA5A8`) is a color-only signal not covered by the stated "no color-only signaling" rule (which only enumerates RSVP state, upload status, and validation errors). Its contrast against a white/muted cell background is ≈2.94:1, under the 3:1 non-text/UI-component contrast guidance — an older or low-vision user may not reliably perceive which days have events before tapping in, and there's no numeric/text fallback (e.g., an event count) specified. (EXPERIENCE.md Component Patterns — Event calendar cell; Accessibility Floor — no-color-only-signaling list). *Fix:* extend the no-color-only rule to explicitly cover the calendar dot (e.g., a small count badge or an accessible day-cell label), and/or deepen the teal for this specific use to clear 3:1.

- **medium** Card and form-input hairline borders (`{colors.border}` #D8D8D8 ≈1.42:1, `{colors.border-strong}` #D1D1D1 ≈1.53:1 against white) are far below the 3:1 non-text-contrast guidance for perceivable UI boundaries. The Elevation section explicitly relies on this hairline alone in default state ("Cards sit flush... with a border hairline rather than a shadow in default state"), so for an older/low-vision user a card edge or an empty form-input's boundary may be nearly invisible until they place a cursor or focus it. (DESIGN.md Elevation & Depth, Colors). *Fix:* darken the default border token (or add a subtle background-fill differentiation on inputs/cards) so field and card boundaries are legible without relying on focus state alone.

- **medium** The 44pt/48dp touch-target minimum is explicitly stated for tab-bar items, gallery tiles, sign-up buttons, and resident-switcher pills, but not for `form-input` fields, `event-calendar-cell` day cells, or the meal-selection rows/"Cancel order" text-link action. Calendar day cells are the highest risk: fitting 7 columns (a week) into a phone-width grid while also hitting 44pt per cell is a real design constraint that isn't called out, so an implementer optimizing for a tight calendar layout could quietly shrink cells below the floor. (EXPERIENCE.md Accessibility Floor; Component Patterns — Event calendar cell, Meal selection row). *Fix:* add form-input, calendar day-cell, and the meal "Cancel order" text-action to the explicit touch-target list, and flag the calendar-cell/7-column tension for implementation.

- **medium** The resident switcher is specified as "a horizontally-scrollable pill row... or dropdown when more than one resident is linked" with no rule for which pattern applies when, and no stated scroll affordance (partial next-pill peek, chevron, scroll shadow) for the pill-row option. For a less tech-fluent user with 3+ linked residents, an undiscovered horizontal-scroll interaction risks a resident's content simply never being found — a real usability/accessibility risk given the explicit "older, less tech-fluent" framing attached to this exact component. (DESIGN.md components.resident-switcher; EXPERIENCE.md Component Patterns — Resident switcher). *Fix:* pick one pattern (or a clear threshold, e.g. pill row for 2–3, dropdown for 4+) and specify a visible scroll cue for the pill-row case.

- **medium** Events offers both a list view and a calendar view, but neither EXPERIENCE.md nor Flow 1 states which is the default. A calendar/grid view is inherently higher cognitive load (paging, grid scanning) than a list for a less tech-fluent audience, and Flow 1's own narrative implicitly uses the list ("sees the coffee morning on Thursday as an `event-list-item`") without the spine ever formalizing that as the default. (EXPERIENCE.md Information Architecture; Key Flows — Flow 1; Component Patterns — Event calendar cell). *Fix:* explicitly set list as the default view for family users, with calendar as an optional secondary toggle.

- **low** Web portal keyboard focus order/Esc/focus-ring behavior is only asserted ("follows shadcn/ui defaults") rather than specified per surface — appropriately light for a non-formal-audit V1, but as written it isn't checkable against anything concrete (e.g., focus-trap and return-focus on the sidebar's mobile sheet, or tab order through attendee-list tables with an adjacent CSV export button). This mainly matters for admin users on desktop who rely on keyboard/screen magnification. (EXPERIENCE.md Accessibility Floor). *Fix:* at minimum, state explicitly that opening/closing a modal or the mobile nav sheet traps and then returns focus — the one place default browser behavior commonly breaks silently — since staff's primary portal entry point is a personal mobile browser where this matters most.

- **low** The hover-only fill `{colors.accent-blue-hover}` (#3C7AD1) with white text computes to ≈4.29:1, under AA for normal text — same category of failure as muted-foreground but low real-world impact since hover states don't apply on touch (the family app's only interaction model) and are transient on desktop. (DESIGN.md Colors). *Fix:* low priority; verify only if this hover fill is ever used to render static label text rather than a transient hover state.

- **low** DESIGN.md's Colors prose states the teal accent is used for "info-toast backgrounds," but the `toast-banner` component spec and EXPERIENCE.md's State Patterns both correctly use `{colors.accent-blue}` for the info/offline toast. Not itself an accessibility failure (accent-blue's contrast is fine), but the inconsistency risks an implementer wiring in the lower-contrast, borderline-failing teal instead. (DESIGN.md Colors vs. Components — toast-banner). *Fix:* remove "info-toast backgrounds" from the teal-accent description to match the component spec.
