- (decision) Multi-tenant isolation: defense-in-depth. Binds: all API/DB access. Prevents: any single missed home_id filter (app bug, raw SQL, new endpoint) from leaking cross-home data. Rule: (1) auth middleware resolves home_id into request-scoped context (AsyncLocalStorage), (2) ORM-level extension auto-injects home_id into every query — developers never write the filter by hand, (3) Postgres RLS enforced with FORCE ROW LEVEL SECURITY on every tenant-scoped table as last line of defense, (4) every tenant-scoped table has a composite index leading with home_id.
- (version) Pattern verified current via web search 2026-07-02: shared-schema + RLS + ORM auto-scoping is the standard 2026 multi-tenant SaaS pattern (Supabase, PlanetScale, Neon). Gotcha confirmed: FORCE ROW LEVEL SECURITY required or table owner bypasses policies.

- (decision) Backend framework + ORM: NestJS 11 (Express v5 adapter, swappable to Fastify adapter later without app rewrite) + Prisma 7 + PostgreSQL 17. Binds: apps/api. Prevents: per-endpoint drift in error envelope, pagination, validation shape, and RBAC checks — Nest Guards/Pipes/Interceptors centralize what Express would leave to per-route discipline.
- (version) Versions verified via web search 2026-07-02: NestJS 11 (Express v5 default adapter), Prisma 7 (Nov 2025, TS-native runtime, official RLS client-extension pattern), PostgreSQL 17.
- (assumption) NestJS learning curve (~3-4 weeks from Express background) accepted as a real cost; mitigated by TS-first alignment with rest of stack and senior dev authoring first reference module for junior to pattern-match.
- (decision) Design paradigm: feature-modular, layered (NestJS modules). Binds: apps/api. Prevents: two features accessing the same data through inconsistent paths. Rule: each module = Controller -> Service -> PrismaService; a module's service is the only entry point other modules may call (no direct cross-module table access, even read-only).
- (decision) Media storage: Cloudinary (not S3). Binds: photo upload/serving. Prevents: team building/maintaining a custom Lambda/Sharp resize+CDN pipeline; satisfies NFR3 (server-side thumbnail compression) and signed/auth-protected media URLs out of the box. Cost premium (~16x/GB vs S3) accepted given team size and PRD's own 0/mo billing-alert plan.
- (decision) Photo upload flow: client requests signed upload params from NestJS backend (Cloudinary Node SDK), uploads binary directly client->Cloudinary (not proxied through API), then confirms to backend which writes the Photo metadata row via Prisma. Prisma/Postgres stores only cloudinary_public_id (+ home_id, resident_id, uploaded_by, caption) — never a pre-built transformation URL. Binds: photo upload/display. Prevents: divergent hardcoded transformation URLs between gallery and full-screen views, and stale URLs if transform strategy changes.
- (version) Cloudinary vs S3 verified via web search 2026-07-02: Cloudinary free tier 25 credits/mo (1 credit = 1000 transforms or 1GB storage/bandwidth), Plus 9/mo for 225 credits; ~16x/GB storage premium vs raw S3 but includes transformation+CDN+signed-URL out of the box. At NFR13's 50k-photo ceiling (~15GB compressed), well within Cloudinary free/Plus tier.

Binds: apps/admin.
