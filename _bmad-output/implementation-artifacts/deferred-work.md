## Deferred from: code review of epics.md (Story 1.6) (2026-08-02)

- **bcryptjs is pure-JS and can block the Node event loop under sustained load.** Chosen deliberately over native `bcrypt` this session to avoid node-gyp/Windows build fragility (see `apps/api/src/auth/password.service.ts`). Accepted tradeoff for now — revisit with worker-thread offloading or native `bcrypt` behind an optional build step if login volume becomes a real concern.

- **`super_admin` carries no `home_id` in the JWT, though AD-8/AD-18's prose lists it alongside staff/admin.** Deferred as a documentation issue, not a code bug: the Prisma schema comment (Phase 0) and AD-1's `@BypassTenantScope()` cross-home model both assume `super_admin` is unscoped, so the code matches the actual intended design. AD-8/AD-18's wording should be corrected to call out `super_admin` as the third home-id-less case alongside `family`, or clarified — worth a small architecture-doc fix later.

- **No per-request re-validation of `isActive`/role, and no refresh-token revocation on logout/refresh.** Accepted stateless-JWT tradeoff: 15-minute access-token TTL bounds the exposure window for a deactivated account or a leaked refresh token. No AD mandates a revocation list and the schema has no table for one. Revisit if/when a real incident or compliance requirement calls for immediate revocation (would need a denylist/jti table).

- **Access and refresh tokens share a single `JWT_SECRET`, discriminated only by a `type` claim.** Matches the original Phase 0 `.env.example` design intent (single secret documented there). The `type` claim is the accepted mitigation against cross-use. Revisit with a dedicated `JWT_REFRESH_SECRET` only if defense-in-depth becomes a priority.

## Deferred from: Story 1.7 — password reset & invited-account activation via email link (2026-08-05)

- **Password-reset email retry backoff (NFR15: 60s → 5min → 30min) is in-process `setTimeout`-based, not a durable queue.** `MailService.sendPasswordResetEmail` schedules its own retries via `setTimeout` rather than a job queue — no queue infra (Redis/BullMQ) exists yet, and the frozen spec explicitly calls this the accepted V1 tradeoff. A pending retry is lost if the API process restarts mid-backoff (e.g. a deploy lands between the 60s and 5min attempts), silently dropping that reset email with no record it needs re-sending. The user can always re-request a reset link, so this degrades to an extra click rather than a hard failure. Revisit with BullMQ/Redis (or a durable outbox table) if email delivery reliability becomes a real complaint. Same in-process limitation means repeated `requestReset` calls for one user within a retry window spin up independent, non-deduplicated retry chains (each can independently report to Sentry on exhaustion) — not worth a partial fix without the same durable-queue infra.

- **`POST /auth/password-reset` is rate-limited per client IP (`@Throttle`, 5/min), not per target email.** Matches the existing codebase convention (`AuthService.login` has the same IP-based limiting) and satisfies NFR10/AD-8's literal requirement, but doesn't stop a multi-IP attacker from email-bombing one victim's inbox with reset requests, or from accumulating several simultaneously-valid outstanding tokens for that account (only a *successful* confirm invalidates a user's other tokens — a bare request does not). Revisit with per-email request counting or CAPTCHA if abuse is observed in practice.

- **`confirmReset` unconditionally sets `isActive: true` on any account reached via a valid token, with no way to distinguish "never-activated invite" from "deliberately deactivated existing account."** Currently unreachable — no feature in this codebase can set an existing user's `isActive` to `false` (Story 1.12, home-admin user/role management, isn't built yet) — so there's no way today to reach this ambiguity. Must be revisited before or when an admin-deactivation feature ships: as written, a deactivated user who still holds an unexpired/unused reset token (or requests a fresh one — `requestReset` has no `isActive` check either) could silently self-reactivate.

## Deferred from: Story 1.3 — super admin assigns a home admin to a care home (2026-08-07)

- **`UsersService.createPendingHomeAdmin` writes `User` then `HomeMembership` as two sequential calls, not one atomic transaction.** `HomeMembership` is tenant-scoped (`TENANT_SCOPED_MODELS`); the tenant-scoping Prisma extension opens its own internal transaction against the base client for every tenant-scoped operation, and nesting that inside an already-open interactive `$transaction` callback is unverified in this codebase (no tenant-scoped model has a write path yet — Phase 2+ modules aren't built). Two independent, already-atomic-on-their-own calls sidesteps that risk. A `try/catch` deletes the orphaned pending `User` if the `HomeMembership` create fails, so a retry doesn't hit the AC #3 email-uniqueness conflict. The remaining gap: a process crash in the narrow window between the two calls (before the catch runs) leaves an orphaned pending `User` with no membership and no password — the affected email is then permanently blocked from being (re-)invited until someone manually deletes that row. Revisit with a proper interactive-transaction-safe pattern (or a scheduled cleanup of stale zero-membership pending users) if this is ever observed in practice; low-probability window, not worth solving speculatively for a single admin-invite action.

## Deferred from: code review of story-1.3-assign-home-admins (2026-08-07)

- **Concurrent identical-email invites can produce a transient false-negative `409`.** If two simultaneous `POST /homes/:id/admins` calls target the same new email, the loser gets a real (if momentary) `409 Conflict`. If the winner's own `HomeMembership` create then fails and triggers its rollback (deleting the winner's `User`), the email becomes available again — but the loser was already told definitively the account exists, with no signal to retry. This is an extension of the sequential-writes tradeoff already accepted in Critical Risk #2 (no interactive `$transaction` around the tenant-scoped `HomeMembership` write); revisit together with that tradeoff if either becomes a real issue in practice.
- **RESOLVED 2026-08-11** — ~~Non-UUID `:id` on `/homes/:id/admins` (and the pre-existing `GET`/`PATCH /homes/:id`) reaches an unguarded Postgres cast, surfacing a raw `500` instead of a clean `404`.~~ Fixed by adding `ParseUUIDPipe` to the `:id` `@Param()` on all three routes (`GET/PATCH /homes/:id`, `POST /homes/:id/admins`) — a malformed id now 400s at the routing layer before any Prisma call. (Note: `ParseUUIDPipe`'s default behavior is `400 Bad Request`, not `404`, which is the standard Nest convention for a malformed identifier vs. a valid-but-nonexistent one — the latter still 404s via `HomesService.findOne`'s existing `NotFoundException`.) Covered by a new e2e case in `homes-invite.e2e-spec.ts` ("rejects a non-UUID :id with 400 instead of a raw 500"). Verified: build, lint, 52 unit tests, and 8 e2e tests (3 suites) all passing against local Postgres.

## Deferred from: code review of story-2-0-fix-revoked-user-reactivation-via-password-reset (2026-08-30)

- **`PasswordResetService.confirmReset`'s new revoked-user guard relies on an unverified invariant in a different file.** The guard (`password-reset.service.ts:75-88`) assumes `UsersService.revokeAccess` (`users.service.ts`) only ever flips `isActive` and never clears `passwordHash` — true today (confirmed by reading `revokeAccess`), and documented in Story 2.0's Dev Notes, but not enforced by any test against `revokeAccess` itself. If a future change to `revokeAccess` ever nulled `passwordHash` on revoke, this guard would silently stop rejecting revoked users. Revisit by adding a regression test in `users.service.spec.ts` asserting `revokeAccess` never touches `passwordHash`, next time that file is touched.

## Deferred from: code review of story-2-1-admins-crean-y-gestionan-perfiles-de-residentes-por-care-home (2026-08-31)

- **Calendar-invalid ISO dates silently roll over instead of being rejected.** `CreateResidentDto`/`UpdateResidentDto`'s `dob` field uses `@IsISO8601({ strict: true })`, which only validates the string's format — a value like `2023-02-30` passes validation, then `new Date('2023-02-30')` in `ResidentsService` silently normalizes it to March 2nd with no error. Low real-world likelihood for a DOB field entered via a `<input type="date">` picker (which won't produce invalid calendar dates itself), but a direct API call could hit it. Revisit with a shared calendar-validity date-validator utility if this pattern recurs across other date fields in future stories, rather than fixing it one DTO at a time.

## Deferred from: code review of story-1-2-super-admin-crea-y-gestiona-care-homes (2026-08-31)

- **`apps/admin/src/lib/api.ts`'s `ApiError` never surfaces a `string[]` validation message.** NestJS's default `ValidationPipe` returns `message` as an array for validation failures; `api.ts`'s error parsing (`errorBody?.message`) only handles the `string` case, so every 400 across the whole app falls back to the generic `response.statusText` ("Bad Request") instead of the real per-field detail. First noticed by Story 1.2's Care Homes screen (its timezone/name validation errors), but it's a shared client bug, not specific to that screen. Revisit by handling `Array.isArray(errorBody.message)` (e.g. join with `, `) in `api.ts`'s shared error parsing — fix it there once, not per-screen.
- **No optimistic-concurrency guard on `CareHomeForm`'s edit path (`apps/admin/src/routes/care-homes.tsx`).** If two super admins edit the same home concurrently, the second PATCH silently overwrites the first's change (lost update) — no `updatedAt`/version check exists anywhere in the app yet to build this against. Low real-world likelihood (few super admins, infrequent home edits). Revisit if concurrent-edit conflicts are ever actually observed, or when a second screen needs the same guard and justifies building shared optimistic-concurrency plumbing once.

## Deferred from: code review of story-1-15-portal-admin-gestiona-usuarios (2026-09-01)

- **No client-side email format validation on any of the Users screen's three invite/create forms.** `type="email"` plus `noValidate` on the `<form>` explicitly disables the browser's native email check in `InviteHomeAdminCard`, `CreateSuperAdminCard`, and `InviteUserForm` (`apps/admin/src/routes/users.tsx`) — the only feedback on a malformed address is a round-trip to the API. Compounds with the existing gap above (`ApiError` never surfaces `string[]` validation messages) — the response is a generic "Bad Request" rather than a specific one. Low severity for an internal admin tool; the same shape of gap exists on every other form in this app (`residents.tsx`, `care-homes.tsx`) for their own fields — not a regression introduced by this diff. Revisit together with the `ApiError` fix above if this ever causes real confusion.
- **Rapid repeated actions on the same `HomeUserRow` can race past the per-row pending-disable window.** A role change immediately followed by a second click (role change or revoke) on the same row can land after the mutation's `isPending` flips back to `false` but before the invalidated `["users"]` query has refetched — the second action then targets a row the server already changed. `UsersService.mapRecordNotFoundViolation` already maps this to a clean "User not found in your home" error rather than a raw 500, so the failure mode is a confusing-but-safe message, not a crash or data corruption. Same class of low-probability race already accepted elsewhere in this codebase (see Story 1.3's deferred concurrent-invite race above). Revisit with `queryClient.setQueryData` optimistic removal, or a mutation queue per row, if this is ever observed in practice.

## Deferred from: architecture discussion (2026-08-05)

- **No job queue (Redis/BullMQ) for background work — deliberately not adopted yet.** The only current background-shaped operation is the password-reset email retry (see the Story 1.7 entry above), which doesn't justify the operational cost of standing up Redis/a worker process on its own. Revisit at Phase 7 (push notifications, per `backend-plan.md`), which needs its own dispatch-with-retry and dead-token handling — at that point there are two real background use cases (email + push), which is enough to justify introducing the queue once and migrating both onto it, rather than accumulating more one-off in-process `setTimeout` retry logic per feature.
