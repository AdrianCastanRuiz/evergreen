Epic 2 built the family-to-resident data model and its access-control boundary: resident CRUD (2.1), the `FamilyLink` model plus `FamilyResidentGuard` (2.2), and the first two real consumers of that guard on the mobile family experience (2.3, 2.4). It also closed a live security gap carried over from Epic 1 (2.0).

## What Went Well

- **Incremental guard rollout across three stories, cleanly scoped.** Story 2.2 built `FamilyResidentGuard` but deliberately did *not* wire it into a live route — it proved AC #5 via an isolated unit test and explicitly deferred consumer wiring to 2.3/2.4. Story 2.3 became the guard's first real route consumer. Story 2.4 then confirmed the guard was actually in its component's request path rather than assuming it "just worked." No speculative code, no premature wiring.
- **Code review kept finding real, non-cosmetic bugs.** Story 2.0: a TOCTOU race between the pre-check and the transaction commit, plus a timing side-channel that let a valid-token holder infer revoked-vs-active status by response latency. Story 2.1: an `update()` bug where `dob: null` was silently coerced the same as "field not sent," making DOB un-clearable. Story 2.2: the guard failed *open* when the tenant-context store was entirely absent, and had no cross-home isolation test for `GET /residents` list. These are the kind of bugs that don't show up until someone is actively trying to break the boundary — review caught all of them pre-merge.
- **Security fix from Epic 1's retro was resolved with more rigor than scoped.** Story 2.0 didn't just add the `isActive` guard clause — the review process surfaced the TOCTOU and timing-leak follow-ons, and Adrian's `revokedAt`-timestamp decision closed a regression (blocking legitimate re-invite reactivation) that a simpler fix would have introduced.

## Challenges / Recurring Patterns

1. **UI was never visually verified across the epic.** Stories 2.1, 2.2, 2.3, and 2.4 — 4 of 5 — all shipped UI (admin Residents screen, Family Links panel, mobile resident switcher, mobile profile card) with zero browser or emulator verification. Each story flagged this honestly in its own Completion Notes, but it's a consistent gap, not a one-off. Backend correctness was covered thoroughly (unit + e2e against real Postgres); visual/layout correctness was not. This matters more entering Epic 3, which adds a 6-type admin content editor plus 6 new mobile consumption screens.
2. **A build-only bug slipped past the standard verification pass.** Story 2.1's `ResidentsService.create()` was missing `homeId` in its Prisma `data` object — invisible to `jest`/`eslint`, only surfaced when `nest start`'s real `ts-loader` compile ran, found post-`done` while booting the dev server. The story's own notes flag that an ad-hoc `tsc --noEmit` "was apparently never actually run" earlier in that session.
3. **Rollback-helper duplication (Epic 1 action item #2) carried through unaddressed.** Story 2.2 extended `UsersService.inviteUser`'s existing manual-rollback `try/catch` correctly (no new duplicate copy), but the underlying ask — extracting one shared helper instead of three hand-rolled copies — still hasn't been done. Two epics open now.
4. **Docker Desktop not running at session start** recurred in Stories 2.0 and 2.1 (both needed local Postgres for e2e). Minor, self-resolved each time, not worth a formal action item — noted for pattern-awareness only.
