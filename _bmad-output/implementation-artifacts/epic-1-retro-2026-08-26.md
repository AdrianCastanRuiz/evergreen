## What Went Well

- The multi-tenant isolation design (Story 1.1) held unchanged across all 14 stories — no story needed to work around or modify the core `home_id` scoping mechanism.
- The invitation/activation pattern (pending user → one-time email link) stayed consistent across Stories 1.3, 1.5, and 1.7 — one mechanism, reused, not reinvented per story.
- Story 1.8 (invite-code onboarding) and Story 1.10 (role-based navigation) shipped together, completing the full family flow end-to-end (onboarding → tab navigation) rather than leaving it half-built.

## Challenges / Recurring Patterns

Found by grepping `code-review finding` comments across the codebase — an honest trail of what review actually caught:

1. **Duplicated multi-step-write rollback logic.** `UsersService.createPendingHomeAdmin` / `createSuperAdmin` / `inviteUser` (Stories 1.3, 1.4, 1.5) each hand-roll the same "create User, then create HomeMembership/token, roll back User on failure" pattern independently, because no interactive `$transaction` can safely wrap a tenant-scoped write yet (documented tradeoff in `deferred-work.md`). The tradeoff itself is fine; the copy-pasted rollback shape three times is the smell.
2. **Same email-trim-before-`@IsEmail()` bug fixed three separate times** (`CreateSuperAdminDto`, `InviteHomeAdminDto`, `InviteUserDto`) instead of a shared validator/decorator built once after the first occurrence.

## Critical Finding — Security Gap (Confirmed Live)

`deferred-work.md`'s Story 1.7 entry (2026-08-05) flagged `confirmReset`'s unconditional `isActive: true` as "currently unreachable" because no feature could deactivate a user yet. **Story 1.12 (home admin revokes access) now sets `isActive: false`, making this reachable.**

Confirmed in `apps/api/src/auth/password-reset.service.ts`: neither `requestReset` nor `confirmReset` checks `isActive`. A revoked user can request (or already hold) a valid reset link and silently reactivate their own account — no admin involvement.

**Decision (Adrian):** High priority, addressed as part of Epic 2's critical path — not an isolated mid-retro hotfix, since Epic 2 sprint planning follows immediately.

## Epic 2 Dependency Check

Story 2.2 ("Admins vinculan cuentas familiares a residentes específicos") assumes a resident-selection step exists inside the Story 1.5 invite flow. Today `POST /users/invites` is API-only — no screen exists in `apps/admin` to invite a user at all.

**Decision (Adrian):** Story 2.2 builds the full invite UI (invite + resident selector) — not split out as separate prep work.

Also noted: `FamilyResidentGuard` (referenced throughout Epic 2's ACs) doesn't exist yet — new build, not carried-over debt.
